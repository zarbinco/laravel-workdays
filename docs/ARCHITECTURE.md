# Complete Definition Sources And Unified Working-Time Calculations

Config and Database are complete, exclusive definition sources. Exactly one source owns shared settings, profiles, inheritance, routing, holidays, working hours, and cutoff for a calculation. `chain`, `hybrid`, independent holiday storage, per-field selection, cross-source inheritance, and silent fallback are rejected. Boot, command discovery, config publishing/caching, and macro registration require no live database.

Start with the [English](en/README.md) or [Persian](fa/README.md) task guides to use the package. This reference explains source boundaries, immutable revisions and shared arithmetic. The [capability matrix](../FEATURE_PRESERVATION_MATRIX.md) maps behavior to implementation and exact tests; [verification](verification.md) explains how to run those checks.

## Definition And Bootstrap Boundaries

The Config source alone reads `workdays.definitions`: required nonblank `default_profile`, native-boolean `include_start_date`, explicit string/integer `hijri.method`/`adjustment`, optional nullable `profile_routing`, and raw named `profiles`. Old operational root keys and `storage.driver` remain errors. Config opens no database and ignores invalid database connection settings. Database does not open or validate file definitions, even if those definitions are malformed.

File-backed `driver`, nullable `database.connection`, positive `max_scan_days`, macro options, and import-tool paths are bootstrap settings. They select or constrain the backend and never override its operational calendar. A null connection resolves the application's default connection when a database operation opens; an invalid explicit connection fails. The chosen connection object/name and revision remain pinned throughout the view. A per-call horizon may narrow the captured safety bound, never enlarge it.

`DefinitionSource::open(): WorkdayDefinitions` remains the injectable source seam. The factory captures selection once; one selector opens Config or Database without engine-specific branches. `WorkdayDefinitions` contains detached shared settings, explicit source provenance, diagnostic revision ID, and lazy raw-profile callbacks. Administrative revision IDs do not enter calendar fingerprints or snapshot schema.

`CalculationContext` applies the same `ProfileConfigResolver`, calendar adapters, logical holiday provider, routing, and calculator cache to both sources. Calculator identity includes profile plus actual scan limit. `profileFor()` routes and constructs from one view; Bulk shares one context while reverse items have independent mutable search state. A retained calculator keeps its view, and each new operation through a long-lived manager opens a fresh one. There is no process-wide head/definition cache, external cache service, manual cache-clear step, or transaction held for a calculator's lifetime.

## Database Schema And Read Lifetime

The explicitly published migration creates only:

| Table | Responsibility |
|---|---|
| `workday_definition_state` | Singleton active-revision pointer used for publication compare-and-swap. |
| `workday_definition_revisions` | Immutable shared settings, schema version, operational content hash, and bounded administrative metadata. |
| `workday_definition_profiles` | Immutable raw JSON profile per revision, with an exact-name digest identity and integrity checks. |

All live holidays are in their owning raw profile. Old `workday_holiday_rules`/`workday_special_dates` models, migrations, and providers are retired; there is no duplicate holiday representation or compatibility bridge. Removing their package files does not drop an application's tables. No automatic schema migration, data conversion, initialization, pruning, or source switch occurs.

Opening a runtime Database view reads the committed active revision and its shared settings. Existence/profile lookups use that revision and connection, cache both present and absent names, and materialize only selected profiles and required ancestors. First access to an R1 parent after R2 publication still queries R1 immutable rows. Profiles include holidays for all dates, so day/slot/pause/reverse evaluation requires no date-by-date SQL. Bulk's validated 1–62-date prefetch hint remains supported but is redundant for materialized revision profiles, including outside its hinted range.

Reads use the selected connection's primary/write PDO without changing the application's overall read/write policy, avoiding a replica observing a new head before its profile rows. A caller-owned transaction controls visibility: it may see its own uncommitted publication or retain an older snapshot according to database isolation. Package publication uses nested transaction support and does not commit or roll back an application's outer transaction. Success inside an outer transaction remains provisional until that transaction commits. A later independent operation sees the committed head permitted by its own connection/transaction visibility.

Before migration, the source reports setup guidance. After migration but before publication, it reports explicit initialization guidance. Missing tables, invalid connections, malformed JSON, failed reads, and corrupt persisted definitions raise `DefinitionSourceException`; they never fall back to Config or become ordinary Bulk-item failures or promise `unresolvable` results.

## Validated Publication And Explicit Transfer

`Configuration/DatabaseDefinitionRepository` is the supported write service:

| Method | Result and contract |
|---|---|
| `current()` | `?Data\DefinitionRevision`; null only for an existing, uninitialized schema. Full administrative raw-document read. |
| `revision(int $revisionId)` | Read an immutable historical raw release for export/rollback. |
| `validate(array $definitions)` | Read-only `Configuration\DefinitionDocument`, with detached `definitions` and deterministic `contentHash`. |
| `publish(array $definitions, ?int $expectedRevisionId, array $metadata = [])` | `Data\DefinitionPublication` exposing `revisionId`, `changed`, and `contentHash`. Expected revision is required; explicit null initializes only an empty source. |

Each publication is a complete replacement. Edit a retrieved raw document, then publish it; omitted profiles/fields are deletions rather than generic dotted-key merge instructions. All profiles, ancestors, default/routing references, and supplied capabilities are validated before publication. Effective inheritance is validated, while raw ownership, `extends`, aliases, omitted keys, nulls, false flags, empty sections, and meaningful list order are stored unchanged. Day-only profiles require neither hours nor cutoff. Explicit cutoff must be valid on the final effective profile before publication.

Shared validation now rejects duplicate weekend aliases and recurring holiday titles other than string/null in both sources; this deliberately tightens malformed-input validation without changing valid numerical outputs. Validation rejects malformed types, unsupported fields, invalid calendar dates/keys/timezones/hours, overlapping seasons, duplicate weekday aliases, missing parents, cycles, dangling references, executable/non-finite/non-UTF-8 values, and invalid JSON. The shared import/publication policy is maximum depth 32, 100,000 data nodes, 10,000 profiles, 255 UTF-8 bytes per profile name, and 4 MiB (4,194,304 bytes) for the complete compact versioned export. Every accepted document can be exported and re-imported within that policy. Definition JSON is parsed strictly; no `unserialize()`, `eval()`, or requiring imported PHP definition documents is used.

Definition integrity hashes use a separate deterministic domain from delivery-promise fingerprints, sort associative keys, and preserve meaningful order/types. Revision IDs, timestamps, and audit metadata are excluded. Integrity detects accidental changes and is not authentication. Optional actor/reason/import metadata is application supplied, bounded, and independent of any application's user table.

The repository validates/builds a candidate, then checks the expected revision and writes revision rows, profile rows, and the active pointer in one configured-connection transaction. Pointer compare-and-swap checks affected rows on SQLite and MySQL; stale expected revisions raise the distinct `DefinitionConflictException`. Explicit null never authorizes overwriting an existing release. No-op content still checks staleness before returning the existing revision with `changed = false`. Failed inserts/pointer switching roll back candidate rows and retain the previous head. Restoring historical content publishes a new revision token rather than resetting the pointer to an old ID. Direct SQL modifications are outside the supported write contract, and package models expose no unrestricted live-row `save()` path.

`workdays:definitions:export` requires an explicit source and protects existing output unless `--force` is given. `workdays:definitions:import` requires exactly one of initialization or expected revision, including for dry-run. The version-1 JSON envelope contains only `format_version` and raw `definitions`; no credentials/bootstrap settings are exported. Explicit transfer may target Database while calculations still use Config, without switching the runtime driver.

The Iran importer uses this publication service. Config supports dataset-only dry-run and rejects writes. Database dry-run compares one pinned release and reports inserts/updates/skips/conflicts; real writes require its expected revision. `--force` permits differing holiday values, never stale tokens or invalid dates. Gregorian/Jalali correspondence, dataset year, duplicates, titles, and source metadata are validated. Inherited holidays participate in conflict/no-op decisions; other profiles, ownership, reopening precedence, routing, and hours remain intact. An identical second import is a no-op. Official annual datasets remain optional local inputs, never fetched or auto-imported.

## Inheritance, Provenance, And Promise Replay

Source-neutral section rules remain: weekends replace; recurring holidays merge by calendar/key; dated maps merge by date; normalized weekday windows replace per weekday; seasonal/extra-day window lists replace; cutoff scalars override and explicit null weekdays remain meaningful; documented empty sections clear inherited content. Missing optional schedule keys stay omitted. Inherited holidays are evaluated under the selected child's identity.

The shared logical provider receives explicit `config`/`database` provenance. Exact-holiday and extra-day reason sources use that label; recurring reasons retain their established `holiday_provider` label. Snapshot `holiday_inputs` metadata explicitly identifies Config or Database. No engine reads Config to guess origin. Equal definitions have equal timestamps, types, windows, stages, eligibility, routing, and reasons apart from those exact source-label fields. Calendar/integrity hashes incorporating those labels may also differ. Same-source Bulk/standalone parity compares complete outputs without masking fields.

Capture calculates the original and bounded evidence from one revision. Restoration validates stored evidence/integrity and performs bounded frozen replay without opening Database or reading current Config. Outer/evidence schema version 1 is unchanged. `Calendar/CalculationSemantics::CURRENT = 2` is the separate numerical contract used by capture and strict restoration. A genuine semantics-1 snapshot fails explicitly even if its payload hashes are valid; no old engine or in-place conversion exists. Unsupported older captures require deliberate regeneration from their original inputs. Editing a version field or recomputing a hash is not a conversion. Calendar fingerprints identify effective calendar content, payload hashes identify stored bytes/content, runtime metadata identifies the execution environment, and Database revision IDs identify publications. None substitutes for the numerical-semantics field.

Relevant hours/cutoff/global settings change `configurationChanged`; holiday inputs change `holidayInputsChanged`; effective Database holiday input changes affect `databaseRulesChanged`. A new administrative revision affecting only an unreferenced profile does not change a selected calendar fingerprint. Current comparison preserves the original result and opens one fresh view; ordinary calendar infeasibility and infrastructure source errors remain distinct. Every restore verifies work/handoff through `WorkingTime` over captured UTC windows. Matching tzdb additionally permits full frozen rule/plan replay, regardless of PHP/Carbon/Verta/Islamic metadata drift or live configuration. Different tzdb retains captured UTC stage consistency, strict structural and transit-microsecond checks, while historical civil-date transit cannot be fully rederived without that historical tzdb. This is a representation limit, not permission to skip work-result validation or invent an old execution environment.

## One Schedule Resolver And Exact Interval Engine

`EffectiveWorkingHours` owns effective daily schedule selection for all profiles. Calendar eligibility gates shifts starting on a date; exact-date overrides precede explicit seasonal weekdays, weekly hours, and the established extra-working-day fallback. Explicit empty date/season overrides suppress fallback, while weekly-empty extra dates retain it. A previous date's valid overnight shift survives a receiving holiday/empty overlay. Genuine overlaps union without duplicate elapsed time; independently touching windows remain distinct for slot grids. `WorkingHours` retains syntax validation, with `allow_overnight_working_hours` only permitting overnight/`24:00` endpoints. It has no numerical-mode selector.

`WorkingTimeBoundary` materializes configured wall clocks on actual civil dates and advances date labels. Strict nonexistent/ambiguous configured boundaries fail with context. A derived missing-midnight start may use the first actual instant of the same date; a wholly skipped date contributes no interval and consumes its offset. `24:00` means the next local date boundary. Valid DST intervals count elapsed UTC time. Unrepresentable ambiguous daily splits fail explicitly.

`BusinessDayCalculator::workingIntervalsFor()` materializes these effective windows once per profile/date/evaluation-timezone within its pinned calculator lifetime. `Support/WorkingTime` is the single exact consumption/measurement/navigation engine. It uses guarded integer UTC microseconds for supported UTC years 0001–9999, never float timestamps or per-fragment minute truncation. Input objects stay immutable. Half-open membership includes opening and excludes closing; previous navigation at isolated closing returns the last microsecond. A duration can complete at closing. Zero minute addition remains identity after validation; finite whole-minute-compatible hour inputs delegate to the same engine.

Differences fix the evaluation timezone from the original first argument, convert the second into it, then order instants and accumulate overlaps. Public minute differences truncate the non-negative total once before applying sign; public hours remain minutes/60. Antisymmetry is a claim within one evaluation timezone. Exact internal durations, rather than rounded public differences, drive work capacity and SLA deadlines.

Every search captures its bound before normalization: input date plus `max_scan_days` offsets for core navigation; one anchored forward budget for positive addition; complete bounded range validation for differences. An exclusive final `24:00` end can complete core work/difference without admitting positive time on the next label. Carry-in ownership lookup does not enlarge the counted interval. Profile-local date margins only represent the owning operation's bounds. Plan, SLA, slot date count, snapshot horizon, reverse lookback and recurrence limits remain distinct and are never reset per stage or increased in Config.

Forward work consumes exact intervals within the actual plan end, replacing rounded daily-capacity preflight/overnight rechecks. Zero stages still normalize to open time, while closing completion does not automatically authorize handoff. Reverse planning uses the same intervals for pruning/search cells and actual forward verification, preserving disconnected DST business-day regions and legitimate exclusive handoff/cutoff microseconds. Exhausted proof budgets or representation errors fail explicitly. SLA reuses the shared intervals and keeps pause union/subtraction, open-pause deadline uncertainty and breach policy separate. Slots use the same schedules/boundaries with their stricter independent-window, midnight and offset-transition policy; candidates away from a transition remain usable.

Day-only eligibility, cutoff date routing, transit and recurrence remain independent of working-hour availability. Bulk dispatches to these same engines within one pinned context, retains typed results and masks no same-source differences. The dedicated working-time search exception remains a collectable domain exhaustion only at its trusted package origin; source/infrastructure/programming and boundary/overflow errors do not become plausible empty calendars.

## Configuration Reads And Verification

Operational reads are confined to `ConfigDefinitionSource` and `DatabaseDefinitionSource`/repository. The context factory/selector captures driver, connection, old-key rejection, and maximum bounds. Framework publishing/dependency binding, macro registration flags, and explicit tool paths remain legitimate bootstrap reads. Planners, SLA, recurrence, reverse, validators, calculator arithmetic, and frozen replay receive explicit dependencies. Source-read audits and behavioral substitution/isolation tests cover this boundary.

Installer `--driver=config|database` publishes requested config and the Database migration only; `--storage` has no alias. It does not migrate, initialize definitions, edit `.env`, or touch application data. Existing installations with older published migrations must review their own schema and upgrade plan explicitly. Test migration changes in an independent disposable database first; copying package files cannot remove published copies or migrate stored data.

A successful changed publication stores every raw profile again, plus shared settings and one state-pointer update. Validation/export are whole-document administrative work; runtime reads are targeted. Retained revisions grow with publication count and document size. There is no automatic deletion because old views must remain readable. Applications own authorization, backups, publication frequency, and storage monitoring.

Its historical MySQL evidence includes exact profile identity, connection/lazy-view isolation, atomic rollback, independent publication races and numerical parity; local results do not establish that remote CI ran.
